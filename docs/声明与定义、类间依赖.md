# 声明与定义、类间依赖

> 以 C++ Primer 第 12 章的 StrBlob / StrBlobPtr 为例，整理"声明 vs 定义"、不完整类型、
> 代码顺序约束，以及互相引用的类如何拆分到多个文件。

## 一、声明与定义

**核心规则：定义一定是声明，声明不一定是定义。**

- **声明（declaration）**：把名字引入程序，只说明"存在这样一个实体"。
- **定义（definition）**：提供使用该实体所需的全部信息——类是完整的成员列表（编译器据此确定对象大小与布局），函数是函数体，变量是分配的存储。

| 实体 | 声明 | 定义 |
|---|---|---|
| 类 | `class StrBlobPtr;`（前向声明） | `class StrBlobPtr { ... };`（本身也算一次声明） |
| 函数 | `string& deref() const;` | `string& StrBlobPtr::deref() const { ... }` |
| 变量 | `extern int x;` | `int x = 5;` |

判断口诀：看到**函数体、类的 `{}` 成员列表、变量的存储分配**，就是定义；只有名字和类型信息，就是声明。

### 类定义的"完整"到什么程度

类定义（`class X { ... };`）要求的是**成员列表**，但两类成员的要求不同：

- **成员函数：只需声明**（签名）。函数体可以放在类外任何位置，甚至另一个 .cpp；当然也可选择在类内内联定义。
- **数据成员：必须是完整类型**。编译器要在类定义处确定对象的大小与布局，所以 `B b;` 要求 B 的类定义在先；而指针/引用成员 `B* p;`、`B& r;` 只需 B 声明过（大小与被指类型无关）。

```cpp
class B { public: void f(); };   // B 定义完成：f 只有声明，完全合法

class A {
    B b;                         // ✓ 数据成员：B 已完整
    B* p;                        // ✓ 指针成员：B 前向声明即可
    void g();                    // ✓ 成员函数：声明即可，函数体在哪都行
};                               // A 至此定义完整
```

## 二、不完整类型与完整类型

- 只经过前向声明的类是**不完整类型（incomplete type）**；出现过类定义之后才是**完整类型**。
- 不完整类型"信息量只够提到它，不够使用它"：

```cpp
class StrBlobPtr;                 // 只有前向声明

// ✓ 不完整类型可以做（只"提到"类型名）
StrBlobPtr* p;                    //   声明指针（指针大小与被指类型无关）
StrBlobPtr& r;                    //   声明引用
StrBlobPtr f();                   //   函数声明的返回类型
void g(StrBlobPtr*);              //   函数声明的参数类型
class StrBlob {
    friend class StrBlobPtr;      //   友元声明
    StrBlobPtr begin();           //   成员函数声明
};

// ✗ 不完整类型不能做（要"使用"实体，需要大小/成员/构造函数信息）
StrBlobPtr obj;                   //   构造对象
new StrBlobPtr;                   //   动态创建
sizeof(StrBlobPtr)                //   求大小
p->incr();                        //   访问成员
class Sub : public StrBlobPtr {}; //   继承（需要基类完整布局）
```

对不完整类型做 ✗ 清单里的事，编译器报
`invalid use of incomplete type 'class StrBlobPtr'`。

## 三、顺序约束：一条硬的，一条软的

**硬约束（唯一一条）**：构造对象、访问成员、需要类型大小的代码之前，必须已见到**类定义**。

**软约束**：函数的**定义**位置完全自由——调用只需要**声明在先**；编译器为调用点生成一条对未解析符号的调用指令，**链接阶段**再与定义对上号。因此成员函数的类外定义可以放在调用点之后，甚至放在另一个 .cpp 里。

### 跨类调用成员函数的细化

A 类的成员函数里调用 B 类的成员函数（`b.f()`），调用点需要见到什么？

- 需要的是 **B 的类定义**，前向声明不够：`.`/`->` 访问成员必须"知道有哪些成员"，B 必须完整。类定义已提供调用所需的全部信息——f 是否存在、签名（参数类型、返回类型）；至于 f 的函数体在哪，调用点不关心。
- **B::f 的定义不需要在调用点之前**，只要存在于程序中某处即可（见下面的链接时机）。
- 时机细节：若调用写在 A 的**内联函数体**里（类内），该函数体在 A 类定义结束处解析，因此 B 的类定义必须出现在 **A 的类定义之前**；若写在 A::g 的类外定义里，则只需在那个类外定义之前。

### 链接发生在链接期，不是运行时

时序是**编译 → 链接 → 运行**，符号解析在第二步就完成了：

1. 编译期：调用点只生成对未解析符号（mangled name，如 `_ZNK10StrBlobPtr5derefEv`）的调用指令；
2. 链接期：链接器（ld）在生成可执行文件时，从所有 .o 里找到定义，把调用地址对上；
3. 若整个程序都没有该定义，**链接期**就报 `undefined reference to ...`——可执行文件根本生成不出来，程序到不了运行阶段。

（进阶例外：使用动态库 .dll/.so 时，符号解析会推迟到加载期甚至首次调用时，那才是"运行时链接"；平时 `g++ a.cpp b.cpp` 生成 exe 是静态链接，全部在链接期完成。）

### 软约束的例外：定义必须可见的实体

普通函数靠链接器兜底，但下列实体要求**定义出现在每个使用它们的翻译单元里**——所以必须放头文件：

| 实体 | 原因 |
|---|---|
| `inline` 函数 | 内联展开需要在调用点看到函数体；ODR 要求各翻译单元定义一致 |
| 模板 | 实例化时按定义生成代码，编译器必须见到定义 |
| `constexpr` 函数 | 编译期求值需要函数体 |
| 类本身 | 构造/访问成员需要完整布局（即硬约束） |

### 互引用类在单文件里的规范排布

```cpp
class StrBlobPtr;                 // ① 前向声明：让 StrBlob 里能声明 begin/end

class StrBlob {                   // ② StrBlob 定义
    friend class StrBlobPtr;
    // ...
    StrBlobPtr begin();           //    只声明（不完整类型可作声明的返回类型）
    StrBlobPtr end();
};

class StrBlobPtr {                // ③ StrBlobPtr 定义
public:                           //    构造函数访问 a.data，需要 StrBlob 完整 + friend —— ②已满足
    StrBlobPtr(const StrBlob &a, size_t sz = 0): wptr(a.data), curr(sz) {}
    string& deref() const;        //    成员函数只声明
    // ...
};

StrBlobPtr StrBlob::begin() {     // ④ begin/end 定义：构造 StrBlobPtr，必须在③之后
    return StrBlobPtr(*this);
}

string& StrBlobPtr::deref() const { ... }   // ⑤ 成员函数定义：位置自由，在③之后即可
```

两个易错点：

1. **类内联函数体也在"硬约束"管辖内**：内联函数体虽然推迟到类定义末尾解析，但若此时依赖的类型仍不完整（如上例把 begin 的函数体直接写在 StrBlob 类内），照样编译失败。依赖其他类的函数体应移到类外。
2. **按值返回不能返回局部对象/临时对象的引用**：`StrBlobPtr& begin() { return StrBlobPtr(*this); }` 返回悬垂引用（临时对象在完整表达式结束即销毁）。接口类（迭代器类）应**按值返回**。

## 四、互引用类拆分到多个文件

看似循环：StrBlobPtr 的构造函数需要 StrBlob 的定义，StrBlob::begin 的定义需要 StrBlobPtr 的定义。

**拆解的关键：循环只存在于"定义"层面。头文件只放声明和前向声明，需要完整类型的定义全部放进 .cpp——头文件之间的依赖就成了单向无环。**

（"头文件"一名译自 header file——header 本义是"信头、页眉"，指置于正文之前、起提纲作用的部分：头文件放接口声明（"有什么"），.cpp 放实现定义（"怎么做"）。与物理位置无关，`#include` 也不强制写在文件开头，只是约定俗成。）

```
StrBlob.h       前向声明 class StrBlobPtr; 定义 StrBlob 类；begin/end 只声明
StrBlobPtr.h    #include "StrBlob.h"；定义 StrBlobPtr 类
StrBlob.cpp     #include "StrBlobPtr.h"；定义 StrBlob::begin/end 及其他成员函数
StrBlobPtr.cpp  定义 StrBlobPtr::check/deref/incr
main.cpp        #include "StrBlobPtr.h"
```

头文件依赖图（无环）：

```
StrBlobPtr.h ──→ StrBlob.h
StrBlob.cpp  ──→ StrBlobPtr.h ──→ StrBlob.h
main.cpp     ──→ StrBlobPtr.h ──→ StrBlob.h
```

在看展开顺序之前，先明确"翻译单元"从何而来：`#include` 是预处理器做的**文本粘贴**——头文件内容被原样贴进 include 的位置，粘贴后的 .cpp 整体才是一个**翻译单元**，编译以翻译单元为单位。由此有一个直接的工程推论：构建配置（如 CMake 的 `add_executable`）只需列出 .cpp——.h 靠粘贴进入翻译单元，构建系统会自动跟踪头文件依赖，头文件改动时重编译对应 .cpp（有些项目把 .h 也列进 add_executable，对编译无影响，纯为 IDE 工程树展示方便）。

编译 `StrBlob.cpp` 这个翻译单元时，include 展开顺序天然满足硬约束：
先见 StrBlob 完整定义 → 再见 StrBlobPtr 完整定义 → 最后编译 begin/end 函数体。

配套规则：

1. **头文件卫士**：类定义在一个翻译单元里只能出现一次（ODR，单一定义规则）。
   `#pragma once` 或 `#ifndef STRBLOB_H / #define / #endif` 防止同一头文件被重复展开。
   （函数、变量的定义全程序只能一份，inline 函数和类除外——类允许多个翻译单元各含一份相同定义。）
   卫士宏名不得与程序中任何标识符同名——实际踩坑（13 章 Folder.h）：写成
   `#ifndef Folder / #define Folder` 会把类名 Folder 定义成空宏，其后所有 Folder
   记号（包括 `class Folder` 这一行本身）都被预处理器替换为空，整个文件无法编译。
   规范做法是用 `FOLDER_H`、`MESSAGE_H` 这类全大写下划线命名。
2. **friend 声明的副作用**：`friend class StrBlobPtr;` 若此前名字未出现过，会把
   StrBlobPtr 声明到友元所在类的**外层命名空间**——即友元声明兼作前向声明。
   显式写一行 `class StrBlobPtr;` 更清晰，是推荐写法。
3. **链接兜底**：StrBlob.cpp 调用的 StrBlobPtr 构造函数，其定义无论内联在 StrBlobPtr.h
   还是在 StrBlobPtr.cpp，链接器都能在链接期对上（即第三节的软约束）。
4. **cpp 文件互不 include**：`#include` 本身不限文件类型，它只是文本粘贴；但把一个 .cpp
   粘贴进多个翻译单元，会让其中的函数定义出现多份，违反 ODR，链接期报
   multiply defined symbol。头文件之所以能被反复 include，正是因为它只放声明
   （inline 函数、模板是"定义必须放头文件"的例外，见第三节）。
   例外技巧：unity build（CMake 的 `UNITY_BUILD`，故意把多个 .cpp 合并成一个翻译单元
   加速编译）、sqlite3.c 之类的单文件合并库——这些是刻意设计，不是日常规范。

### 另一个例子：13 章的 Message/Folder

互引用类不一定非要互相 include——**include 的方向由"谁需要对方的完整类型"决定**。
13 章的拆分（本仓库 13/ 目录）：

```
Folder.h     只前向声明 class Message;  —— 数据成员只有 set<Message*>，存指针只需前向声明
Message.h    #include "Folder.h"        —— 让编译 Message 成员函数体的翻译单元见到 Folder 完整定义
```

依赖图仍是单向无环：Message.h → Folder.h。严格说，Message.h 自身也只存
`set<Folder*>`，按"按需 include"的原则，它也可以只前向声明 Folder，把
`#include "Folder.h"` 挪进 Message.cpp（save 的函数体要调 f.addMsg(...)，
访问成员才真正需要 Folder 的完整定义）——两种拆法依赖都无环。而 Folder 的
析构函数若要访问 `m->folders`，在 Folder.cpp 里 `#include "Message.h"` 即可，
依然不成环：环只存在于"定义"层面，定义下沉到 .cpp 就能断开。

这个例子还展示了**友元关系不对称、不传递**：

- Folder 声明 `friend class Message;`，Message 的成员函数（save/remove/析构）
  才能调用 Folder 私有的 addMsg/remMsg；但这**不覆盖**自由函数 swap——swap 是
  Message 的友元而非成员，友元身份不随之传递——Folder 必须另行声明
  `friend void swap(Message&, Message&);`。
- Message 也声明 `friend class Folder;`，因为 Folder 的析构/拷贝操作反过来要
  访问 Message 私有的 folders 集合。友元是单向授权，双方各自声明。

## 五、小结

- 声明引入名字，定义提供实体；定义 ⊇ 声明。
- 类定义的"完整"只看成员列表：成员函数有声明即可，函数体可以在任何地方；**数据成员必须是完整类型**。
- 前向声明得到不完整类型：能"提到"，不能"使用"（构造、访问成员、求大小）。
- 顺序硬约束只有一条：构造对象/访问成员之前必须见到类定义——所以跨类调用 `b.f()` 要求 B 的**类定义**在先，而 B::f 的函数体可以在程序任何角落。
- 函数定义由链接器在**链接期**解析：缺定义是构建期的 `undefined reference`，不是运行时错误；例外是 inline / 模板 / constexpr，它们的定义必须对每个使用它的翻译单元可见（放头文件）。
- 互引用类拆文件：头文件互相只留前向声明，定义下沉到 .cpp，环即断开。
- `#include` 是文本粘贴，粘贴后的 .cpp 整体才是翻译单元：构建配置只列 .cpp，.h 靠粘贴进入并由构建系统跟踪依赖；.cpp 之间互不 include，否则函数定义会在多个翻译单元里各出现一份，违反 ODR（multiply defined symbol）。
- 类之间的 include 方向由"谁需要对方的完整类型"决定：只存指针/引用则前向声明即可，访问成员才需要完整定义——把这类 include 下沉到真正需要它的 .cpp，互引用类的环总能断开。
- 友元关系不对称、不传递：双方各自声明自己的 friend；`friend class X` 只覆盖 X 的成员函数，不覆盖 X 的友元自由函数。
